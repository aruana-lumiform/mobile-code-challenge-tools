# mobile-code-challenge-tools

Hosting for the Android code challenge fixtures: the document JSON the candidate's
app fetches, and the images that JSON references. Everything is static and served
over HTTPS by GitHub Pages, so a candidate can point Retrofit at it with no API key,
no CORS setup, and no rate limit.

## Setup

The **Deploy challenge site** workflow enables Pages itself on its first run
(`configure-pages` with `enablement: true`), so there is nothing to switch on by
hand. Publishing is therefore just:

1. Push to the repository's default branch, or run the workflow manually from the
   Actions tab. It validates `challenge.json` and then publishes `public/`.
2. Wait for the first deployment; Pages can take a couple of minutes to answer on a
   brand-new site.
3. Confirm the endpoint is live and typed correctly:

   ```bash
   curl -i https://aruana-lumiform.github.io/mobile-code-challenge-tools/code-challenge/challenge.json
   ```

   Expect `HTTP/2 200` and `content-type: application/json; charset=utf-8`.

The deploy job only runs on the repository's default branch, because GitHub Pages
refuses deployments from anywhere else. It reads that branch from the repository
itself rather than hard-coding a name, so renaming the default branch (for example to
`main`) does not break it. Pull requests run the validation job alone.

If the automatic enablement is ever refused — it needs the workflow's `pages: write`
permission, and Pages on a private repository needs a paid plan — switch it on by hand
under **Settings → Pages → Build and deployment → Source: _GitHub Actions_** and
re-run the workflow.

## Changing the content

Everything published lives under `public/`; the directory is uploaded verbatim.

- **Edit the document** — change `public/code-challenge/challenge.json`, then run
  `python3 scripts/validate.py`. It checks that the JSON parses, that every node
  uses a known type with the fields that type requires, and that every image `src`
  points at a file that actually exists in `public/` — a broken `src` is the one
  failure a candidate cannot work around.
- **Add an image** — drop the file in `public/code-challenge/` and reference it as
  `https://aruana-lumiform.github.io/mobile-code-challenge-tools/code-challenge/<file>`.
  The two existing placeholders are generated by `scripts/generate_images.py`
  (needs `pillow`); edit the `IMAGES` list there and re-run it to restyle them.
- **Rename or transfer the repo** — update `OWNER`/`REPO` at the top of
  `scripts/validate.py` and the absolute URLs inside `challenge.json`; the validator
  will fail loudly until the two agree.

Pushing to the default branch redeploys. Pages sends `Cache-Control: max-age=600`,
so an updated JSON can take up to ten minutes to reach a client that already fetched it.

## Notes for the Retrofit side

These are the properties of the hosting that matter when the candidate wires up
Retrofit — worth knowing when you review their submission:

- **Base URL must keep its trailing slash**, and the `@GET` path must not start with
  one, or Retrofit resolves it against the host root and drops the repository segment:

  ```kotlin
  Retrofit.Builder()
      .baseUrl("https://aruana-lumiform.github.io/mobile-code-challenge-tools/")
      .build()

  @GET("code-challenge/challenge.json")
  suspend fun getDocument(): DocumentDto
  ```

- **HTTPS only**, so no `usesCleartextTraffic` / network security config is needed.
- **`application/json; charset=utf-8`** is the response content type. Retrofit picks a
  converter by return type rather than by response content type, so Gson, Moshi and
  kotlinx.serialization all work here.
- **The response is a single object, not an array**, and it is recursive: `items` holds
  a mix of `page`, `section`, `text`, `question` and `image` nodes, discriminated by
  `type`. Modelling that is the interesting part of the challenge — sealed classes plus
  a polymorphic adapter (Moshi `PolymorphicJsonAdapterFactory`, kotlinx.serialization
  `@JsonClassDiscriminator`, or a custom Gson `TypeAdapterFactory`).
- **`ETag` and `Cache-Control: max-age=600`** are sent, so OkHttp's cache can serve a
  repeat request without hitting the network. Useful for the offline requirement, but
  it can also mask a broken offline path while testing — verify offline behaviour with
  a cleared cache, or with airplane mode after a cold start.
- **Images are ~1600x1000 JPEGs**, large enough that loading a thumbnail at full
  resolution is a visible mistake, which is the point of the "reduced size" requirement.

## Repository layout

```
public/                          # published verbatim to GitHub Pages
  index.html                     # landing page listing the URLs
  .nojekyll                      # never let Jekyll rewrite these files
  code-challenge/
    challenge.json               # the endpoint
    welcome.jpg, chapter1.jpg    # images referenced by the JSON
scripts/
  validate.py                    # structure + asset check, also runs in CI
  generate_images.py             # regenerates the placeholder JPEGs
.github/workflows/
  deploy-pages.yml               # validate, then publish public/
```

## If you would rather serve the JSON from a Gist

A Gist works for the JSON, but not for the images — Gists are for text files, so
`welcome.jpg` and `chapter1.jpg` still need to live here. If you want the Gist anyway,
paste the contents of `public/code-challenge/challenge.json` into a public Gist named
`challenge.json` and hand out:

```
https://gist.githubusercontent.com/<user>/<gist-id>/raw/challenge.json
```

Leaving the revision hash out of that URL keeps it pointing at the latest revision.
Two trade-offs to know about: raw Gist responses are served as `text/plain` rather than
`application/json` (harmless for Retrofit, as noted above, but it misrepresents the
endpoint), and the content is then split across two places that can drift apart —
the validator here cannot check a Gist it does not own.
